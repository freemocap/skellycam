# Contributing to SkellyCam

We love your input and we need your help! We want to make contributing to this project as easy and transparent as possible, whether it's reporting a bug, discussing the current state of the code, submitting a fix, proposing new features, or becoming a maintainer.

## Development with GitHub

We use GitHub to host code, track issues and feature requests, and accept pull requests.

## GitHub Flow

We use [GitHub Flow](https://guides.github.com/introduction/flow/index.html), so all code changes happen through pull requests:

1. Fork the repo and create your branch from `development`.
2. If you've added code that should be tested, add tests.
3. If you've changed APIs, update the documentation.
4. Ensure the test suite passes.
5. Make sure your code lints (`uv run ruff check skellycam/`).
6. Issue that pull request!

## Licensing

Any contributions you make will be under the AGPL Software License. When you submit code changes, your submissions are understood to be under the same [AGPL](https://github.com/freemocap/skellycam/blob/main/LICENSE) that covers the project.

## Reporting Bugs

We use [GitHub Issues](https://github.com/freemocap/skellycam/issues) to track bugs. Report a bug by [opening a new issue](https://github.com/freemocap/skellycam/issues/new).

**Great bug reports** tend to have:

- A quick summary and/or background
- Steps to reproduce (be specific!)
- Include an uploaded ZIP of the skellycam recording session you ran that produced the issue
- What you expected would happen
- What actually happens
- Notes (possibly including why you think this might be happening, or stuff you tried that didn't work)

## Pull Request Guidelines

- Any code that comes through a PR should be covered with tests
- Those tests must pass the GitHub Actions workflow before they may be merged
- Any UI changes should include a small video of the working application with the change included

## A Note on Review Timelines

We're a small team, and as Nadia Eghbal describes in [*Working in Public*](https://press.stripe.com/working-in-public), developer attention is the primary limiting resource in open-source projects. Please be patient with pull request reviews — they can take time, especially when the team is focused on core development work.

A few things that affect review priority:

- **Contributions touching [hot or hard loops](/docs/technical/architecture#hot-hard-and-soft-loops)** — the frame capture pipeline, synchronization gate, shared memory, and timestamp logic — receive much higher scrutiny than changes to soft loops (UI, streaming, logging). We don't meant to gatekeep, but a subtle bug in these parts of the code can silently corrupt scientific data and downstream processing pipelines.
- **First-time contributors**: consider reaching out on the [Discord server](https://discord.gg/SgdnzbHDTG) before investing significant time. We're happy to discuss approach and scope before you write the code and let you know where your proposed work fits in to our planned development roadmap.
- **Smaller, focused PRs** are reviewed faster than large ones. When in doubt, split your work into multiple PRs.

## Coding Style

We use [Ruff](https://docs.astral.sh/ruff/) for linting. Run `uv run ruff check skellycam/` to check and `uv run ruff check --fix skellycam/` to auto-fix.

See the [Development guide](./) for more details on the development workflow.

## Type System Conventions

SkellyCam uses [beartype](https://beartype.readthedocs.io/) for runtime type checking across the entire package. This means **type annotations are enforced at runtime** — if you pass the wrong type to an annotated function, you'll get a `BeartypeCallHintParamViolation` immediately at the call site. This is intentional and should not be suppressed. If beartype catches a violation, fix the type, not the check.

When adding new code, use the right type system for the layer:

- **Pydantic `BaseModel`** — Only for types that face untrusted input from the frontend (HTTP request/response bodies, API models). These benefit from Pydantic's validation, coercion, and OpenAPI schema generation.
- **`@dataclass`** — For internal containers, IPC infrastructure, and anything that holds multiprocessing primitives or numpy arrays. No serialization overhead, no `arbitrary_types_allowed` workarounds needed.
- **`msgspec.Struct`** — For types that are serialized at high frequency over the WebSocket. Fast JSON encoding without the overhead of Pydantic's `model_dump()`.

As a rule of thumb: if the type never leaves the Python backend as JSON, it should be a dataclass. If it's serialized to JSON more than once per second, it should be a `msgspec.Struct`. If it validates user input from the API, it should be Pydantic.

All WebSocket JSON message types are defined in `skellycam/api/websocket/websocket_message_types.py` as a `WebsocketMessageType(str, enum.Enum)`. When adding new message types, add them to this enum — do not use raw strings.
