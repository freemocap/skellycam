# openpnp-capture pre-built artifacts — wish list for Skellycam consumption

## What we need

Skellycam's Rust engine links openpnp-capture **statically**. At build time,
`build.rs` needs to find two static libraries plus their headers for the
current target platform. At runtime, everything is baked into the `.pyd` —
end users never see these files.

### Static libraries — 6 targets (maximal coverage)

| # | Rust target triple | Who runs on this |
|---|---|---|
| 1 | `x86_64-pc-windows-msvc` | Windows 10/11 on Intel/AMD — the vast majority of Windows users |
| 2 | `aarch64-pc-windows-msvc` | Windows on ARM — Snapdragon X laptops, Surface Pro 11, growing fast in 2026 |
| 3 | `x86_64-apple-darwin` | Intel Macs (2010–2020) — millions still in use, especially in education/labs |
| 4 | `aarch64-apple-darwin` | Apple Silicon Macs (M1/M2/M3/M4) — all Macs sold since late 2020 |
| 5 | `x86_64-unknown-linux-gnu` | Linux on Intel/AMD — Ubuntu, Fedora, Debian, etc. Standard desktops and laptops |
| 6 | `aarch64-unknown-linux-gnu` | Linux on 64-bit ARM — **Raspberry Pi 4 and Pi 5**, also AWS Graviton, newer SBCs |

### Why these six and not more

**Not including `i686-pc-windows-msvc` (32-bit Windows):** Python.org stopped
shipping 32-bit Windows installers at Python 3.11. Skellycam requires 3.11+.
This target has no user base left.

**Not including `armv7-unknown-linux-gnueabihf` (32-bit ARM Linux):**
Raspberry Pi 3 was the last Pi restricted to 32-bit. Pi 3 can run the 64-bit
Raspberry Pi OS (arm64). Pi 4 and Pi 5 are natively 64-bit. The `aarch64`
target covers all Raspberry Pi hardware from Pi 3 onward. Adding `armv7`
would cover some very old SBCs (BeagleBone Black, original Pi 2) but they
lack the CPU power to run a camera capture pipeline at usable framerates
anyway.

### Headers

The minimum set of C headers needed to generate/verify FFI bindings:

- `openpnp-capture.h` — the main public API
- Any internal headers needed for context/stream type definitions

(Our current `camera/ffi.rs` hand-writes the FFI declarations, but a
canonical header makes it easy to regenerate or verify bindings via
`bindgen` later.)

## How they should be packaged

### GitHub Releases

Each release of the openpnp-capture fork produces one archive per target
triple, uploaded as a GitHub Release asset:

```
Release v2.0.0
├── openpnp-capture-windows-x86_64.zip
├── openpnp-capture-windows-arm64.zip
├── openpnp-capture-macos-x86_64.tar.gz
├── openpnp-capture-macos-arm64.tar.gz
├── openpnp-capture-linux-x86_64.tar.gz
└── openpnp-capture-linux-arm64.tar.gz
```

Each archive contains the same internal structure:
```
lib/
  openpnp-capture.lib   (or .a on unix)
  turbojpeg-static.lib  (or .a on unix)
include/
  openpnp-capture.h
```

All archives share the same internal directory structure (`lib/` +
`include/`) so consumption code can be identical across platforms.

### Stable URLs

GitHub Releases produce stable redirect URLs:

```
https://github.com/USER/openpnp-capture/releases/download/v2.0.0/openpnp-capture-windows-x86_64.zip
```

This URL pattern is deterministic given a tag name. `build.rs` can
construct it at build time and download/extract with a simple HTTP GET.

## How Skellycam consumes them

### Option A — build.rs downloads at compile time (recommended)

`skellycam-rust/skellycam/build.rs`:

1. Detects the target triple via `std::env::var("TARGET")` or `cfg!()` macros
2. Constructs the download URL from a pinned version constant
3. Downloads the archive to `target/build-artifacts/` (cached across rebuilds)
4. Extracts it
5. Adds `cargo:rustc-link-search` and `cargo:rustc-link-lib` directives

Caching: the archive is downloaded once. Incremental builds skip the
download. A clean build or version bump re-downloads.

This means **no developer needs to install cmake, MSVC, clang, or any C
toolchain beyond what Rust already requires.** Rust on Windows already
needs the MSVC link.exe (which comes with Visual Studio Build Tools or
the Rust installer's `windows-msvc` target). That same linker is what
consumes the `.lib` file — no extra C compiler needed.

### Option B — a proper `openpnp-capture-sys` Rust crate (nice-to-have)

A separate crate published to crates.io would:

- Contain the raw FFI bindings (generated by `bindgen` or hand-written, feature-gated)
- Use the same download mechanism in its own `build.rs`
- Export a `-sys` API that higher-level crates depend on
- Handle versioning independently

Then skellycam would just add `openpnp-capture-sys = "2"` to `Cargo.toml`
and the linking is handled transparently.

This is the Right Way™ for the Rust ecosystem but adds maintenance burden.
For now, Option A inside skellycam's `build.rs` is simpler and sufficient.

## CI / GitHub Actions on the openpnp-capture repo

A single workflow that:
1. Triggers on push to a release branch or on tag creation
2. Builds openpnp-capture for all four target triples (matrix build)
3. Packages each target's `lib/` + `include/` into an archive
4. Creates a GitHub Release and uploads all archives as assets

The release tag determines the version number used in the download URLs.

### Example workflow structure

```yaml
# .github/workflows/release.yml
on:
  push:
    tags: ["v*"]

jobs:
  build:
    strategy:
      matrix:
        include:
          - target: windows-x86_64
            os: windows-latest
          - target: windows-arm64
            os: windows-latest       # cross-compile or native ARM runner
          - target: macos-x86_64
            os: macos-13            # last Intel Mac runner (deprecated after mid-2025)
          - target: macos-arm64
            os: macos-latest        # Apple Silicon (M-series)
          - target: linux-x86_64
            os: ubuntu-latest
          - target: linux-arm64
            os: ubuntu-24.04-arm    # native ARM64 runner (public preview)

    steps:
      - uses: actions/checkout@v4
      - name: Build
        run: |
          mkdir build && cd build
          cmake .. -DCMAKE_BUILD_TYPE=Release
          cmake --build . --config Release
      - name: Package
        run: |
          mkdir -p artifact/lib artifact/include
          cp build/openpnp-capture.lib artifact/lib/     # or .a on unix
          cp build/libjpeg-turbo/install/lib/turbojpeg-static.lib artifact/lib/
          cp ../src/openpnp-capture.h artifact/include/
      - name: Upload to release
        uses: softprops/action-gh-release@v2
        with:
          files: |
            artifact/openpnp-capture-${{ matrix.target }}.*
```

## Versioning

Skellycam pins a specific openpnp-capture release version. When
openpnp-capture changes, the version constant in `build.rs` is bumped.
This is intentional — you control when Skellycam picks up C-side changes.

```rust
// In skellycam build.rs
const OPENPNP_VERSION: &str = "v2.0.0";
```

## What this means for Skellycam developers

```
git clone skellycam
cd skellycam
uv sync          # ← builds Rust via maturin → build.rs downloads
                 #   openpnp-capture pre-built libs → links → .pyd
python -m skellycam
```

No cmake. No C compiler. No submodules. Just Rust (which `uv` / maturin
already requires for the PyO3 build step).

## What this means for Skellycam users

```
pip install skellycam   # ← gets a pre-built wheel from PyPI
python -m skellycam
```

The wheel already contains the `.pyd` with openpnp-capture statically
linked. Users never download or touch openpnp-capture at all.
